Source code is order-dependent: for all `combinations(range(35),2)`, if both endpoints and their entire LineString are strictly within original concave hull and `d>0`, and `d<=2*Lc`, it calculates `redundancy=max(0,1-d/Lc)`, `c=clip((x_j−x_i)/d,−1,1)`, `w_fwd=exp(−d/Lw)*c` if `c>0.7071` else 0, `w_back=−exp(−d/Lw)*c` if `−c>0.7071` else 0. The source coefficient is `beta*redundancy+delta*(w_fwd+w_back)`; terms with absolute coefficient <=1e−12 are omitted. Free/free terms become quadratic `q_ij*x_i*x_j` and free/fixed terms are **added in source loop order** to free-site linear terms; fixed/fixed are ignored for the optimization objective. All scenarios use the same original water-line-geometry decisions and one-hop feasibility.

Algebraically, `w_fwd+w_back = exp(−d/Lw)*abs(c)` whenever `abs(c)>0.7071`, otherwise 0. Thus changing `c` to `−c`, which reverses the east–west alignment direction in this symmetric *unordered-pair* interaction, does not change the resulting wake penalty. This is an **east–west alignment proxy**, not validated downstream transport. Because the formula is for a symmetric pair, this algebraic identity does not by itself prove anything about physical current directions, wastewater transport or changes from actual hydrodynamic models.
